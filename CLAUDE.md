# canvas-mcp-lite

Lean, instructor-focused Canvas LMS MCP server built on FastMCP. Flat layout; unit tests in `tests/` (`.venv/bin/python -m pytest -q`, no network — Google/Canvas calls are monkeypatched).

## Architecture

All source lives in the `canvas_mcp_lite/` package directory:

- `server.py` — FastMCP entry point. Registers every tool from `tools/`. Tools are grouped into `READ_TOOLS`, `WRITE_TOOLS`, and `DELETE_TOOLS` lists — the grouping documents intent (all register identically). **When adding a tool, add it to the correct list.**
- `client.py` — async Canvas API client (httpx). Bearer auth from `.env`, `canvas_request` for single calls, `canvas_paginated` for Link-header pagination (defaults `per_page=100`), retry with exponential backoff, but **only when safe**: reads retry on timeouts/5xx/rate-limit; writes (POST/PUT) retry only on connect errors and the rate limiter, never on read timeouts or 5xx — Canvas appends a submission comment on every PUT, so a blind retry double-posts feedback (this was a real bug). Pass `idempotent=True` for writes that are safe to repeat. Raises `CanvasAPIError` on non-2xx.
- `util.py` — `get_course_id` resolves a numeric ID or `course_code` string (5-minute TTL cache; do not make it permanent — stale code→ID mappings were a real bug), `format_date`, `announcement_posting_status`.
- `google_client.py` — Google Drive/Docs/Slides API client (`google_request` takes a Drive-relative path or an absolute URL for the Docs and Slides APIs; one `auth/drive` scope covers all three). Used for grading Google Docs submissions in place and for reading/editing Google Slides decks. Auth is a long-lived OAuth **refresh token**: from the env (`GOOGLE_OAUTH_REFRESH_TOKEN`), or a runtime override set by the in-chat connect flow (runtime wins). Tools return the setup message (not an exception) when unconfigured.
- `google_oauth_flow.py` — in-chat account connection for HTTP deployments: the `connect_google_docs` tool mints a single-use state and returns a sign-in link; the public `/oauth/google/callback` route (registered in server.py) exchanges the code, activates the token in-process, and shows it for persisting to the env. States are the security gate — only the tool (behind the secret `MCP_PATH`) can mint one; keep it that way. Requires a **Web application** OAuth client. `google_auth.py` (`canvas-mcp-google-auth`) is the terminal flow for local stdio servers (Desktop-app OAuth client).
- `tools/` — one module per domain: courses, modules_pages, assignments, announcements, discussions, files, quizzes, grading, messaging, peer_review, analytics, integrity, google_docs, google_slides, new_quizzes. `new_quizzes` calls `/api/quiz/v1` at the site root (absolute URL through `canvas_request`); its item-analysis report is generated asynchronously (POST reports → poll `/progress/:id` → download the signed `results.url` without the Canvas token). **Quiz creation** (`create_quiz`/`add_quiz_questions` for Classic, `create_new_quiz`/`add_new_quiz_items` for New Quizzes, plus the two deletes) shares one `questions_json` format defined in `tools/quiz_questions.py`, which validates it and translates each question into either API's payload — keep both translations there. Live-verified gotchas: Classic's answer parser reads the form-style names (`answer_exact`/`answer_error_margin`/`answer_range_start`/`answer_range_end`, `answer_comment` singular) and silently zeroes/drops the names the API docs list, so both are sent; a Classic quiz's `question_count` only refreshes on publish, so count via `GET /questions`. Both create tools add questions before publishing and stop at the first rejected question, telling the caller to append the rest rather than re-create. The `/canvas-quiz` project skill (`.claude/skills/canvas-quiz/SKILL.md`) is the drafting workflow on top of these tools. Grading tools look up the submission's `attempt` first and pin comments to it (`comment[attempt]`), so a resubmitting student sees feedback on the latest attempt only. The same lookup returns existing comments, and every grading tool (single, rubric, bulk) skips posting a comment identical to one already on the submission, so a repeated call after a lost reply is harmless. `analytics.get_student_grades` is the per-student view (enrollment grades + every published assignment's status, optionally the student's standing in the instructor's other courses via `/users/:id/enrollments`) — point graders at it before zeros or "has this student checked out" judgments. `google_docs.comment_on_google_doc` posts real Google Docs comments as the connected account. With `quoted_text` it anchors the comment to that passage via the Docs API `insertComment` (Developer Preview; needs the Docs API enabled in the Cloud project), falling back to an unanchored Drive comment with the quote in the card and saying so in the reply. Never send Drive's `anchor` field — Docs renders it as "Original content deleted". `google_docs` also edits docs directly (`edit_google_doc_text`, `insert_text_in_google_doc`, `replace_text_in_google_doc`) through Docs API batchUpdate, reusing `_locate_range` for passage matching; deleteContentRange runs before insertText at the same start index, and end-of-doc appends use `endOfSegmentLocation` with a leading newline. These are real edits (no suggesting mode in the API) — docstrings steer feedback on student work to comments. `google_slides` edits decks **in place** through the Slides API (`slides.googleapis.com`, same Drive scope): `read_google_slides` prints object IDs, and the edit tools turn them into batchUpdate requests (deleteText ALL + insertText; the delete is skipped on empty shapes because the API rejects it; table cells are addressed as `tableId:row:col`; `- ` lines become createParagraphBullets). New slides pick placeholder IDs up front via `placeholderIdMappings`, which must match the chosen predefined layout; speaker notes need a second call because the notes shape ID only exists after creation. Comments on decks are plain Drive comments (no text-range anchoring for Slides).

## Conventions

- Every tool is an `async def` returning a **formatted human-readable string** (not JSON) — output is read directly by an LLM. Follow the existing `f"ID: ...\nName: ..."` style.
- Course-scoped tools take `course_identifier: Union[str, int]` as the first param and start with `course_id = await get_course_id(course_identifier)`.
- Docstrings ARE the MCP tool descriptions. Encode workflow hints there (e.g. "use get_submission_content before grade_submission"; "peer_reviews=True must be set before assign_peer_review works").
- Safe defaults: create things unpublished (`published=False`); delete-tool docstrings must state the action is permanent.
- File/text extraction goes through `files.download_and_extract_text` (PDF via pypdf, DOCX via python-docx, plain text; 25MB cap). Reuse it rather than downloading directly.

## Packaging (important)

- Packaged as `canvas_mcp_lite` (see `pyproject.toml`) with **relative imports** (`from .tools import ...`) — it runs as an installed package (`canvas-mcp-lite` console script), never `python server.py` directly. Source lives in `canvas_mcp_lite/`; installed editable into `.venv` (`uv pip install --python .venv/bin/python -e .`).
- `.env` at the repo root (with `CANVAS_API_URL`, `CANVAS_API_TOKEN`) is loaded relative to the package location (`client.py` resolves `parent.parent / ".env"`), not cwd — MCP clients launch the server from arbitrary directories. Keep it that way.
- Railway deploy config lives in `.railway/railway.py` (Infrastructure as Code; the old `railway.json` is gone). It declares the `canvas-mcp-lite` service's start command and lists every dashboard variable as `preserve()` — **removing an env entry there makes `railway config apply` delete that variable**, so keep all secrets listed. Workflow: `railway config plan` to preview, `railway config apply` to push (interactive confirm); both need the `railway-sdk` dev extra on PATH (`PATH="$PWD/.venv/bin:$PATH" railway config plan`). `railway up` still deploys the code; config changes go through `railway config apply`.
